# How to Use the Fynsera Guide

Fynsera is an open-source, practical guide for people building AI-native products and companies. It combines software engineering, agent design, evaluation, finance controls, deployment, and startup operations.

The guide does not promise business outcomes. Results depend on the problem, market, implementation quality, operating discipline, and legal environment.

## What the Guide Contains

The curriculum currently includes:

- AI-driven development foundations and tool selection
- Markdown, prompt, and context engineering
- Specification-driven development
- Python and TypeScript foundations
- Agent frameworks, reusable skills, MCP, and conversational interfaces
- Cloud-native deployment, LLM operations, and agent evaluation
- Realtime voice agents, agentic frontends, and physical AI
- A startup guide covering validation, finance controls, human approvals, and responsible blockchain use

Use the chapter navigation to inspect the complete curriculum.

## Evidence Standard

Fynsera separates facts, recommendations, and examples:

- **Facts** should be supported by a primary or clearly identified source.
- **Recommendations** describe a proposed practice, not a guaranteed result.
- **Examples** are illustrative unless they are explicitly identified as measured case studies.
- **Financial, legal, tax, and compliance decisions** require review by qualified professionals.

When a chapter contains a number, benchmark, or product capability, verify it against the linked source and the current product documentation before relying on it.

## Recommended Starting Path

If you are building a company, begin with the [Fynsera Startup Guide](./startup-guide). Validate one narrow customer workflow before investing in a large agent platform.

If you are building technical capability, start with the introductory sections and follow the curriculum in order. Build small evaluated systems as you progress.

## What “AI-Native” Means Here

In this guide, an AI-native product uses models or agents as core product components. The surrounding system still needs ordinary engineering:

- explicit permissions and constrained tools
- structured state and audit trails
- evaluations based on representative examples
- human approval for sensitive or high-impact actions
- monitoring, incident handling, and financial controls

The objective is not maximum autonomy. The objective is useful, measurable work performed within clear boundaries.
